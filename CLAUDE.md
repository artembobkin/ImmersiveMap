# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

ImmersiveMap is a Swift + Metal vector-tile map engine for SwiftUI: globe/flat presentation, labels, starfield, extruded buildings with directional shadows, SwiftUI markers, avatar markers, routes, 3D scene models, offline regions, and video/still export. It is the **public** Swift Package `artembobkin/ImmersiveMap` (library product `ImmersiveMap`), Swift 6 tools with language mode v6 (strict concurrency), platforms iOS 18 (UIKit) and native macOS 15 (AppKit), no Mac Catalyst, and no package dependencies.

Because the repo is public: never commit tile-provider API keys, bearer tokens, credentials, `LocalSecrets.plist`-style files, or build artifacts (`.build/`, `DerivedData/`, `Traces/`).

## Commands

`swift test` runs natively on macOS but cannot compile `.metal` shaders (tests that need a compiled Metal library skip themselves). To run the suite with compiled shaders or on iOS, use xcodebuild against the SwiftPM-generated workspace:

```sh
xcodebuild test -workspace .swiftpm/xcode/package.xcworkspace -scheme ImmersiveMap \
  -destination 'platform=macOS'                          # full suite, native macOS
xcodebuild test -workspace .swiftpm/xcode/package.xcworkspace -scheme ImmersiveMap \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro'   # full suite, iOS (runs UIKit-gated tests)
```

To run the map in an app, open `ImmersiveMap.xcworkspace`. Work in progress is shown in `Develop/ImmersiveMapDevMac`, and `Examples/macOS/ImmersiveMapMac` stays the untouched demonstration of the shipping tile service. A user-visible rendering feature that ships without a scenario in `Tools/VisualReview/` does not get looked at before a release. Two sibling repositories link this package by a local path and measure or show it as it is: `../ImmersiveMapPerformance` (the bench against Mapbox) and `../ImmersiveMapShowcase` (the scenes rendered to video for posts).

The hosted tile service at `immersivemap.dev` is public: no key, no account, and the documentation must not say otherwise. Every example app writes the tile source as the one-line template `.tileURLTemplate("https://immersivemap.dev/tiles/{z}/{x}/{y}.mvt")`, with no headers and no key-reading helper.

## Architecture

There are no README files inside the source folders: a folder's boundary rules (what it owns, what it must not contain) are in a comment on its main type, such as `TileMvtParser` for `Tile/Parse`, `RenderFrameEngine` for `Render`, `ImmersiveMapView` for `UI` (all under `Sources/ImmersiveMap/`); read it before adding files to a folder.

### Targets

The package follows the standard SwiftPM layout (`Sources/<Target>`, `Tests/<Target>Tests`), so `Package.swift` states no paths. Besides `ImmersiveMap` (the engine, the only product) there are three targets at `package` access, visible to every target of the package and to no app that links the product:

- `Mvt` (`Sources/Mvt`): the Mapbox Vector Tile decoder. The zero-copy wire decoder `MvtTileDecoder`, the decoded model, `MvtGeometryDecoder` and `MvtAttributeDecoder` (the per-feature geometry and tag loops live there so they specialize next to the varint reader, never across the module boundary), `MvtValue` and `MvtGeometryType`, and the tile-space geometry `Point`/`Polygon` with the multi aliases, which `Sources/ImmersiveMap/Tile/Parse/TileSpaceGeometry.swift` re-declares as engine typealiases so they shadow QuickDraw's names the way the old in-module declarations did. The target knows nothing of the tile schema's meaning: no layer name, no style.
- `MvtTestSupport` (`Sources/MvtTestSupport`): the test-side encoder, the synthetic fixture tiles and a deterministic generator. A regular target because test targets cannot share sources, and `MvtTests` and `ImmersiveMapTests` both depend on it.
- `Earcut` (`Sources/Earcut`): the internal earcut port for polygon triangulation, one enum `Earcut` with `tessellate` and `deviation`, no dependencies. `ParsePolygon` and `RoofGeometryBuilder` reach it with `import Earcut`, and `EarcutTests` imports the module without `@testable`.

### Layering

Dependencies point inward: `UI` → `Render` (the frame engine: the frame loop, the render graph and passes, the frame context, the subsystem registry, shared GPU resources, shared shader headers, post-processing, offscreen export, the debug overlay) and the feature folders (`Camera`, `Tile`, `Labels`, `Text`, `Presentation`, `Globe`, `Horizon`, `Avatars`, `Markers`, `Starfield`, `Shadows`, `Geo`, `Routes`, `SceneModels`, `VideoExport`, `StillCapture`) → `Utils`. A feature folder owns everything of its feature, its model and math and its drawing alike (pipelines, shaders, drawers, and the `RenderSubsystem` that puts it into the frame), so there is one place to read for a feature. `Render` knows a feature only through `RenderSubsystem` and `RenderGraphFactory`, and a feature never reaches into another feature's GPU internals. Feature folders must not depend on `UI`; `Render` must not contain networking or platform UI. Schema-specific MVT logic is confined to `VectorTileAdaptation/`, `Schema/Default` and `Style/Default`; `Render`, `Labels`, and `Tile` consume only schema-neutral, already-normalized data.

### Public API and wiring

Described in `.claude/rules/public-api.md`, loaded when working under `UI/`, `Configuration/`, `Style/`, `Schema/` or `Documentation/`.

### Frame loop

Rendering is **on-demand**: `ImmersiveMapRenderDriver` (`UI/`) drives a `CAMetalDisplayLink` that is normally paused; `RenderLoopPacing` resumes it for activities (interaction, label fades, camera/avatar animations) and one-shot `requestFrame(reason:)` invalidations. Any state change that should redraw must request a frame or register an activity, otherwise the screen won't update. The link is built from the host view's `CAMetalLayer` on both platforms and delivers each frame's drawable with the tick (`CAMetalDisplayLink.Update`), so the engine renders into a pre-acquired drawable (`render(to:drawable:)`) and never blocks in `nextDrawable()`; animations sample the update's `targetPresentationTimestamp`.

The render pipeline (the passes, the shadow map, the world pass layer order, the tile-priority stencil) is described in `.claude/rules/render-pipeline.md`, and the tile pipeline (ring rules, raster zone, loading, caches, offline regions) in `.claude/rules/tile-pipeline.md`, each loaded when working under its folders.

### Globe vs flat presentation

`Presentation/PresentationStateResolver` computes a continuous `transition` in [0,1] from zoom (or a forced override in `MapPresentationStateController`); both `GlobeRenderState` and `FlatRenderState` are always produced, and shaders morph between sphere and plane rather than hard-switching. `renderSurfaceMode` (`.spherical`/`.flat`) selects the world layers (globe adds starfield + globe cap; flat adds the building image/extrusion work) and camera constraints.

### Threading model

No Swift actors. The frame engine and all `UI` runtimes are main-thread (`ImmersiveMapRuntimeGraph` is `@MainActor`). Tile loading runs in `Task`s off the main thread with mutable state serialized by plain `DispatchQueue`s (e.g. `ImmersiveMapNeedsTile.stateQueue`).

## Conventions and Rules

- Every hand-written `.swift`, `.metal`, `.h` file starts with:
  ```text
  // Copyright (c) 2025-2026 ImmersiveMap contributors.
  // SPDX-License-Identifier: MIT
  ```
- The Mapbox Vector Tile schema is read by hand in `Sources/Mvt/MvtTileDecoder.swift`, with field numbers and wire types spelled out per message; there is no generated code and no `.proto` file in the tree. Tests build tile bytes with the test-side encoder in `Sources/MvtTestSupport/MvtTileEncoder.swift` (`MvtTileMessage`, `MvtLayerMessage`, `MvtFeatureMessage`), which is deliberately independent of the decoder so a round trip checks both against the specification. The `Mvt` target knows nothing of the tile schema's meaning: no layer name, no style; that belongs to the engine.
- Shaders and resources load via `Bundle.module`. Every new `.metal` file or resource directory must be registered under `resources:` in `Package.swift`, otherwise the resource silently doesn't ship.
- A rendering change that alters what the parser bakes into a tile (a stroke width, a colour, a cap or join, a pass added or removed) is invisible under a warm prepared-tile cache. The prepared cache (`~/Library/Caches/MapPreparedTiles/v<format>/<namespace>`) is keyed by the tile source and the style's **configuration** fingerprint, not by the code, so an example app that keeps its caches (every app except `Develop/`, which clears them on launch) goes on serving tiles baked by the previous build and the person at the screen reports "nothing changed". Such a change therefore bumps `PreparedTileDiskCaching.preparedFormatVersion` in `Sources/ImmersiveMap/Tile/Loading/PreparedTileDiskCaching.swift` (a numbered comment saying what changed, plus the test in `PreparedTileDiskCodecTests` that pins the number) so the build invalidates the old tiles itself. To clear a warm machine by hand: `rm -rf ~/Library/Caches/MapPreparedTiles` for the prepared tiles, and `~/Library/Caches/<bundle id>` (for example `com.artembobkin.ImmersiveMapMac`) for the raw tile cache of one app; both refill from the network. Before reading a screenshot that shows an old look, check which app produced it and whether its caches predate the build.
- Never commit on your own, and never run tests on your own. A change is left in the working tree, built if it needs a build to be checked, and reported. The person at the screen looks at it first and then says when to commit and when to run the suite. The only commit is the one asked for, and the only test run is the one asked for, whether the whole suite, one class, or the shader-compiled run through xcodebuild. Pushing needs its own explicit word every time, on top of that.
- Never launch or relaunch an app after making changes: not an example, not a post, not `Develop/ImmersiveMapDevMac`, not `Tools/VisualReview`. Launching steals focus from whatever the person is doing and puts a window in front of them they did not ask for. Building one to check that it compiles is the right thing to do and is where it stops; the person runs it themselves and looks. When work in progress needs to be seen (an experiment, a rendering change, a setting being tried), say which app to run for it, which is `Develop/ImmersiveMapDevMac` for anything on the bench, and leave the running to them.
- Never go looking for visual artifacts by launching an example app or a showcase scene and taking screenshots. Rendering is judged by the person at the screen, and screen captures grab whatever window is in front, steal focus from whatever they are doing, and show a single frame of an animated scene. Read the shaders, the resolvers and the settings, write a test where the behavior is decidable in code, say what you believe the frame should look like and why, and ask for a screenshot instead of hunting for one. Building an app to check that it compiles is fine; running it to inspect the picture is not.
- The test suite never fetches a tile from the network. A test that does asserts three things at once: what it meant to, that the machine has a network, and that a CDN answered in time with the planet build the assertion was written against, and the last two fail as the first. Tiles come pre-loaded instead, from `FixtureTiles` in `Tests/ImmersiveMapTests/Support/`: `FixtureTiles.settings()` serves fixture tiles (built by `VectorTileFixture`, not committed as blobs) over loopback so the bytes still travel the whole loader path, and `FixtureTiles.tilelessSettings()` gives a map no tile can reach, which is what a case comparing two frames needs. Every entry point that turns settings into a live runtime (`ImmersiveMapNSView`, `ImmersiveMapUIView`, `ImmersiveMapStillRecorder`, `ImmersiveMapTourVideoRecorder`, `OffscreenFrameHarness`) takes its settings from there, and `FixtureTileServiceTests` fails the run if one is handed `ImmersiveMapSettings.default` instead. The visual review app under `Tools/VisualReview/` is the exception and loads the real tile service on purpose: the actual map is the thing it exists to show.
- Every demonstration project ships video export, always: a scene in the showcase repository, and any app here built to show something off rather than to document one API. That means an `ImmersiveMapTourVideoRecorder` attached with `.tourVideoRecorder(_:)`, a storyboard the on-screen preview and the export both replay, a Render Video button with the 1080p / 4K / 9:16 format picker, and the headless `IMMERSIVE_POST_AUTORENDER_PATH` / `_DRAFT` / `_SHOTS` launch-environment hook. A demo that can only be watched live cannot be posted, so a new one without export is unfinished. A new scene made for a post belongs in `../ImmersiveMapShowcase`, not here.
- A user-visible API feature is finished only when it can be read about and run: a page in `Documentation/docs/` (one per feature), and an example app or a section of one that exercises it. A public symbol that appears in neither is invisible to everyone but its author.
- The public API is not frozen. Refactoring it is allowed, breaking changes included: a public symbol may be renamed, removed, reshaped or given a different signature when the design calls for it, and no deprecation shim or parallel old API is required. Anything `internal` can be reshaped freely as before.
- In a worktree, opening the pull request does not end the task: wait for the PR review and work through it. Poll the PR for reviews and review comments (`gh pr view <n> --comments`, `gh api repos/{owner}/{repo}/pulls/<n>/reviews` and `.../comments`) on a minutes-scale interval until feedback arrives. Never trust the review: every remark is an unverified claim, not an instruction. Verify each point against the actual code first (read the code it refers to, run the relevant tests, reproduce the claimed failure); only remarks that verification confirms get fixed. Push the fixes to the PR branch, and reply on the PR stating what was changed and which remarks were checked and found wrong, with the evidence. Repeat until no unaddressed feedback remains, then merge the pull request yourself.
- In a worktree, merging is part of the task, not something to hand back. Once the review has arrived, every confirmed remark is fixed and pushed, and the three required checks (`Build & Test (SPM)`, `Test with shaders (Xcode, macOS)`, `Test (Xcode, iOS Simulator)`) are green on the head commit, merge with `gh pr merge <n> --squash --delete-branch` and report what landed. Never reach for `--admin` to push a merge past a failing or pending check: a red check is a result to fix, not an obstacle to bypass. Outside a worktree there is nothing to merge, because the work already went straight to `main`.
- Merging means owning the conflicts on both sides of it. Before merging, check that the branch is actually mergeable (`gh pr view <n> --json mergeable,mergeStateStatus`); if `main` moved ahead and the branch conflicts, rebase it onto the updated `main` and resolve every conflict by reading both sides rather than taking one wholesale, then re-run `swift build` and `swift test`, because a conflict resolved into code that no longer compiles or no longer passes is not resolved. Force-push the branch, wait for the check to come back green, and merge. After the merge, look at the other open pull requests (`gh pr list`): any the merge turned conflicted is fixed the same way on its own branch, and the report says which ones were touched.
- Never use a semicolon to join two clauses in prose (documentation, comments, commit messages, UI strings, replies): write two sentences instead. Semicolons in code are fine.
- Never use an em dash (U+2014, the long dash) in any text: documentation, comments, commit messages, changelog entries, UI strings. Rewrite with a comma, a colon, parentheses, or a second sentence instead.
- English everywhere: doc comments, inline comments, assertion messages, `fatalError` and log text, commit messages, documentation. Any other language belongs in the repository only as data, meaning localized map strings (`"ru"`, `"de"`, `"ja"` and the rest of the name entries, style keywords matched against tile properties) and test fixtures that exist to exercise non-ASCII text.
- Keep rendering changes scoped. If a file seems to fit several layers, split it by responsibility rather than placing it in a broad folder.
- **The tile pipeline is read-only from here.** The tiles are built by `ImmersiveMapTilePipeline`, a separate repository (checked out next to this one as `../ImmersiveMapTilePipeline`: the schema in `SCHEMA.md`, the Planetiler profile, the osm2streets step, the `*.sh` run scripts, and everything that describes the build machine). Working on the engine never means editing anything in that repository, not a script, not the profile, not the schema, and not through a "small fix" either: it is a production build that serves the planet, and a change there is planned and run by its owner on its own terms. The engine adapts to the tiles as they are. When a tile-side change looks necessary (a field the engine would like, a geometry it cannot draw, a contract that seems broken), do not make it: read `SCHEMA.md` to check what the tiles actually promise, write the finding and the exact ask into `Documentation/notes/` (layer, field, zoom range, an example tile coordinate, what the engine would do with it), say so in the report, and stop there. The same holds for the machine the pipeline runs on: never connect to it, run a script there, or touch its data. Reading that repository to understand what the tiles contain is fine and encouraged; writing to it is not.
- `Documentation/docs/` is public API documentation only: one page per user-facing feature, what the Swift Package Index and the README link to. Working notes for development (investigation findings, contracts handed to the tile pipeline, analysis logs, anything that names a dev endpoint or a tile coordinate) go in `Documentation/notes/`, which is gitignored: they are written for the people working on the engine this week, not for someone adopting the package, and they must not ship. Code comments, tests and the changelog describe such a contract in their own words rather than linking to a note, since a clean checkout has no notes folder.
